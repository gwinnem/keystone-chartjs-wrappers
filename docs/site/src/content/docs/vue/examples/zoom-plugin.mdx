The `zoom` prop draws on a local port of `chartjs-plugin-zoom`. Like
[gradient](/vue/examples/gradient-plugin) and
[image label](/vue/examples/image-label-plugin), it isn't a dependency
on a third-party package at all — its logic is ported directly into
`keystone-chartjs-core` (`src/zoomPlugin.ts`).

:::caution[Real scope limitation, not a bug]
This port drops every Hammer.js-dependent code path — pinch-zoom, and
the gesture-driven pan interaction — since Hammer.js itself is
unmaintained (confirmed via a real, open upstream issue). Mouse-wheel
zoom, mouse-drag-to-zoom-rectangle (with Escape-to-cancel), and the
full programmatic API (`chart.zoom()`, `chart.resetZoom()`, `chart.pan()`,
and more) are all kept. A real, honest finding from dissecting the
original source: it has no mouse-only drag-to-pan mechanism at all —
`pan()` was only ever driven by Hammer's own gesture recognizer — so
dropping Hammer.js means dropping *all* interactive pan, not just
touch-pan. `chart.pan()` stays callable programmatically (see the
pan buttons below), just with no built-in drag gesture wired to it.
:::

Being local code rather than a dynamic import also means this example is
genuinely live on this docs site — unlike the
[timestack](/vue/examples/timestack-scale) example, which still hits a
docs-site build-pipeline gap around dynamic imports (its own real
`luxon` dependency currently can't be resolved the same way).

:::tip[`zoom` has no required config, unlike `annotation`]
`annotation` has no plain-boolean form — `AnnotationPluginOptions.annotations`
is required, since there's no sensible empty default. `zoom` and
`dataLabels` both accept either `true` or a config object; see
[Plugins](/vue/api/plugins/) for the full prop reference.
:::
